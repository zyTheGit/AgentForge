## 1. 核心判断

**规则正文投影的价值正在被行业收敛侵蚀；资产落点投影、学习闭环与技能分发在中短期尚无收敛信号。**

AGENTS.md 正在成为跨 CLI 的事实标准（Codex、Gemini CLI、Cursor 等均已采纳）。PRD §2 问题陈述 #1「多工具规则格式碎片化」会随标准收敛**部分**自我消解——四个内置 target 读同一文件的那天，只投影规则正文的工具失去存在理由。

**但收敛只吃掉规则正文这一层。** 本产品的投影落点远不止正文：skills 物化（`on_demand` 在四家是三种表示）、MCP transport 三态逐格归一化（能力矩阵 `src/core/project/projectors/mcp-transport.ts` 的 `MCP_TRANSPORT_MATRIX`，两格显式降级）、commands 命名空间与 `$1..$9`、codex `hooks.json`——这些格式各家自成体系。所以判断应精化为：**规则正文的投影会被标准吃掉；资产落点的投影中短期尚无跨 CLI 收敛信号**。注意口径是「中短期尚无信号」而非「不会收敛」——后者是绝对化断言，一旦上游开始统一技能目录与 MCP 配置就会失效。

这里有个值得点破的差值：**输入侧在标准化（SKILL.md 被多家采纳），输出侧（各 CLI 的技能目录、MCP 配置、命令落点）依然各自为政**——这个差值恰好就是本产品 Skills 分发的生存空间，也反过来加强了 §2.1 把 Skills 升为主打叙事的结论。**但这个差值本身是暂态的**：若输出侧日后也随输入侧收敛，skills 分发让位，learning + SoT 才是终局资产。资产定义不焊死在这个暂态上。

PRD §1.4 差异化中的两项同样不随标准收敛而贬值：

1. **Learning 闭环**（learn → 打分/衰减 → promote → 可审计、可回滚）；
2. **habits 探测 + SoT 分层治理**（user/project 两级、marker 保护、CI 漂移门禁）。

因此建议把产品分层重述为：**规则正文投影是会被标准吃掉的出口层；资产落点投影 + learning + SoT 是资产层**。PRD 2.0 的问题陈述应从「格式碎片化」改写为「Agent 的项目知识无法沉淀、复用和治理」。

## 2. 三档分级

### 2.1 持久做（下一阶段全部工程投入集中于此）

| 投入项 | 理由 | 首要动作 |
|--------|------|----------|
| Learning 闭环（`learn` / `learnings` / `promote` / `auto_capture`） | 最深的护城河（另一项见 §1 列表第 2 条）。**待验证假设**：瓶颈在**捕获**不在管理——捕获不顺手，闭环不会跑起来，存储/打分/衰减做得再好都是空的。该假设目前无用户证据（§3.1 的信号尚未采集），因此首要动作只取不依赖上游能力的那几项 | ① 打磨 `prompt` 档协议正文（常量在 `src/core/learning/auto-capture.ts`）；② 提升 `aforge learn` 非 HTTP 通道的**可发现性**——stdin / `--file` / 免交互路径**均已实现**（`learn.ts`：无参数 TTY 交互、`--file <path>\|-`、非 TTY 报 ConfigError(2)），要补的是 README / docs 的管道示例（`--file -` 从 stdin 读的是**条目正文**；`--print-protocol` 输出的是给 agent 看的协议，两者不可对接）；③ 给无钩子能力的三家文档化 `learn --print-protocol` 的手工挂载写法（**文档项，不计入工程投入**）。**不含 claude 侧 hook 落点**——该项已随 issue [#56](https://github.com/zyTheGit/AgentForge/issues/56) 决议不做（理由见 [learning](learning.md#另外三家将来要支持的前置条件)，登记见 [roadmap](roadmap.md) Phase 3）；要重启得先给出「收益 > 风险面」的新证据，learning.md 记录的四条安全条件（白名单键路径、只增不减、条目带标记、用户手改处置）仍是硬门槛 |
| Skills 跨 CLI 分发（**主叙事**） | 用户感知最强的第二叙事；主路径可用（四家投影、`expose_as_command`、`on_demand` 均已实现）；SKILL.md 输入侧标准化 + 输出侧碎片化的差值即生存空间（§1） | **准入前置**：对外宣称「主打」之前，必须先完成 [#54](https://github.com/zyTheGit/AgentForge/issues/54) 中 codex 显式 `$name` 调用的实机验证。在此之前对外表述维持「主路径可用、待实证」，不先扩能力面 |
| MCP transport 可靠性（**交付保障，不作主叙事**） | 三态逐格归一化 + 两格显式降级已实现（`MCP_TRANSPORT_MATRIX`），它保的是「不静默失真」的信任，不是获客叙事 | 只做维护；[#66](https://github.com/zyTheGit/AgentForge/issues/66)（pi × `sse` 实机连接）随时可做。**不与 Skills 合并宣称「均已验证」** |
| sync 事务化内核（marker 保护、回滚、幂等、`doctor`、两级合并） | 信任基石——用户敢用是因为「不碰我的手写内容」 | 只做维护与打磨，不加新面 |
| CI 漂移门禁 | 团队/企业故事的入口，成本低收益高 | 已有雏形（[ci](ci.md)），保持跟进上游 CLI 配置变化 |

**本节两条红线（评审双方一致，不随分级调整）**

1. **无实证不宣称**：任何「主打 / 已支持」的对外叙事，必须先补齐该项自己列出的实机验证缺口；没有实证时只能写「主路径可用、待实证」。
2. **不为覆盖面放松 learning 的安全前提**：[learning](learning.md#另外三家将来要支持的前置条件) 记录的四条（只作用于白名单键路径、数组只增不减、AgentForge 条目带可识别标记、定义用户手改条目的处置）是硬门槛。放松它们换来的覆盖面会把护城河变成信任负债。

### 2.3 砍掉（建议裁决，需按 §4.2 决议流程确认后执行）

#### 2.3.1 「template / source 深化」的具体口径

「深化」不是一句话，落到具体条目是下面五项。现状基线：模板解析已是四层优先级（内置短路 → 项目层 → 用户层 → 已登记且启用的源），local + git pin 两类源、tag 固定、离线降级、孤儿缓存不参与解析均已实现——**作为「个人 + 团队私有源」的工具已经完整**。

| # | 深化条目 | 内容 | 建议裁决 |
|---|----------|------|------|
| 1 | manifest 做成真实约束 | `manifest.templates[].path` 目前是纯说明字段、不参与解析，id 必须恰好对应 `templates/<id>.md` 相对路径，否则「列得出、解析不到」；深化 = manifest 成为解析事实源 + `source add/update` 时校验 + doctor 检查项 | 随官方源裁剪一并放弃 |
| 2 | 版本语义 | pin 是 user 层登记表里的一个 `ref`、全机器共享——**项目无法各自 pin 同一源的不同版本**；深化 = 项目层 pin 覆盖、semver 区间、`source update` diff 预览 | **幸存者**：项目层 pin 是五条里唯一对应真实场景（多项目共用一个团队私有源、版本需求各异）的，若未来有团队用户反馈再单独立项 |
| 3 | 模板组合能力 | 模板间引用/继承、变量 schema（声明所需 habits 变量、sync 前校验）、错误定位到模板行；会重新撕开已决议的「helper / partial 不予实现」口子 | 放弃 |
| 4 | 供应链信任 | checksum、签名、内容审计。**模板正文是注入 Agent 上下文的指令文本**，第三方模板源本质是 prompt injection 供应链，一旦鼓励生态即背上永久信任责任 | 放弃（这也是裁掉整个生态路线的最重理由） |
| 5 | 发现与分发 | registry、search、安装量——即做成真正的包管理器 | 放弃 |

前两条属修补性质（各约 1–2 个 PR），第 3–5 条是产品级投入；五条合起来 = 做一个 npm。需求侧证据：官方仓库至今没有 `manifest.yaml`，即**零供给**，多源模板生态目前是零用户假想需求。

**幸存者口径**：收缩为三档（内置 `base/default` + 本地 `templates/` + git pin）之后，归入「维护」而非「深化」的只有两项——① 文档口径核查（见 §2.3.2，已完成核实）；② 项目层 pin（条件触发：真有团队私有源用户反馈版本冲突）。

#### 2.3.2 口径分歧核实记录（2026-09-03）

评审过程中发现 [roadmap](roadmap.md) Phase 2 边界与 [commands.md](commands.md#官方模板源默认注册默认禁用) 对「`disable` 能否挡住缓存渲染」口径相反。已核实代码事实：`src/core/sources/render-scope.ts` 即 issue #55 的实现侧修复（commit b723a03，PR #61），`enabled` 是渲染参与判据，禁用源的模板一律解析不到。**commands.md 口径正确**；roadmap 已随本评审同步修正（与本档同一 PR 提交）。#55 的 `disable` 半已修复，剩余仅「官方仓库缺 manifest」一半，随 §2.3 官方源裁剪决议一并处理。

## 3. 条件判断（唯一可能改写上表的触发器）

**如果用户信号显示最强烈的需求是接入 Cursor / Copilot / Gemini 等更大覆盖面**，则：

- 解冻声明式适配器，用数据-only 适配器扩 target；
- 其余分级不变。

### 3.1 信号口径：不再挂在「10 名首次用户」上

PRD §8 L1 那条门禁至今零执行记录，仓库里既无计划书、问卷，也无计时脚本（`tests/e2e/ACCEPTANCE.md` 是 Spec §11.2 的 16 条自动化清单，与用户测试是两件事）。以当前项目规模，凑 10 名首次用户是不现实的前置；把整份分级挂在它上面，等于让本档长期悬空。因此把触发信号降级为两条可执行的替代：

- **量化项**：**主证据是入库 `scripts/` 的自动计时脚本**（干净 Windows 环境采集 init 耗时），**≥ 3 名独立 dogfood 参与者只作佐证**。判据为双指标：**全员 ≤ 5 分钟**（沿用 PRD §8 L1 第 1 条的门禁值）且 **P50 ≤ 3 分钟**（对齐 PRD §8 L3 的 TTFP 值）。
  - 为什么不保留 P90：3–5 人样本下 P90 ≈ 最慢单人，一人环境异常即判死，无统计意义。
  - 为什么主证据必须是脚本：小样本下「全员 ≤ 5min」本质仍是 max 判据，与 P90 同样脆弱；靠脚本在干净环境重复采集才是可核查的主证据，人数只用来暴露交互卡点。
  - **该口径调整需在 PRD 2.0 里同步改写 §8**（含样本量 10 → ≥ 3 的原委注记，避免后人读成门禁缩水；P50 需与 §8 L3 的 TTFP 相互引用），否则又是一处文档分歧。
- **定性项（两级解冻）**：target 扩展的用户信号分两档——**单个附带完整使用场景说明的 issue 只解冻「调研」**（读上游配置格式、评估数据-only 适配器可行性，不写实现）；**≥ 2 个独立来源的同类请求才解冻「实现」**。避免产品方向被第一个提需求的用户绑架，也避免有场景的请求被无限搁置。

顺序仍是：**先拿到信号，再定 target 扩展**，其余裁剪不受信号影响。
